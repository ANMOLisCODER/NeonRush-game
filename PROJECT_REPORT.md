# NEON METRO RUSH — Project Report

**An Original 3D Endless Runner for the Web**
*Computer Graphics Major Project — Academic Report*

---

## 1. Abstract

Neon Metro Rush is a browser-based, third-person, lane-based 3D endless runner
set in an original futuristic Indian metro city at night. The project
demonstrates a complete real-time graphics pipeline on the web: procedural
geometry and texture generation, hierarchical transformation and animation,
perspective projection with an animated follow camera, physically-based and
emissive materials, shadow mapping, fog-based depth cueing, a custom-GLSL
particle system, bounding-volume collision detection, seeded procedural level
generation with formally validated fairness constraints, object pooling and
instancing for performance, and a fully procedural Web Audio soundtrack. All
assets — textures, models, characters, signage and audio — are generated by
original code at runtime; the project contains no third-party creative assets.
The result is a playable, polished game that doubles as a reference
implementation of the core topics of an undergraduate Computer Graphics course.

## 2. Introduction

Endless runners are one of the most recognisable real-time 3D genres on mobile
and web platforms. Their apparent simplicity hides a dense concentration of
graphics and engineering problems: an unbounded world must be streamed from a
bounded memory budget; a camera must follow a fast-moving actor without
inducing motion sickness; difficulty must rise while remaining provably fair;
and everything must run at interactive frame rates on commodity hardware.
This project uses the genre as a vehicle to implement, measure and document
the classical computer-graphics curriculum inside a single coherent product.

## 3. Problem Statement

Build a complete, original, performant 3D endless runner that (a) runs in a
plain browser with no backend, (b) demonstrates the required graphics concepts
visibly and documentably, (c) is provably fair in its procedural generation,
(d) uses only original or permissively licensed assets, and (e) ships with
automated tests, lint-clean code, a passing production build and complete
documentation.

## 4. Objectives

1. Real-time 3D rendering with correct projection, lighting, materials, shadows, fog and colour management.
2. Procedural character construction and procedural (keyframe-free) animation.
3. Smooth third-person camera with speed-reactive framing and optional shake reduction.
4. Seeded procedural world generation with recycled chunks and fairness guarantees.
5. Robust collision detection matched to visible geometry and player pose.
6. Complete game loop: score, multiplier, lives, power-ups, difficulty stages, persistence.
7. Performance engineering: pooling, instancing, light budgeting, pixel-ratio caps, clamped delta time.
8. Professional UI/UX across desktop and mobile, including accessibility-conscious contrast.
9. Procedural audio synthesis compliant with autoplay policies.
10. Testable architecture: pure logic modules under Vitest; E2E smoke validation in headless Chromium.

## 5. Scope

In scope: WebGL rendering via Three.js; gameplay systems; procedural assets;
DOM-based UI; local persistence; static deployment.
Out of scope: multiplayer, backend services, in-app purchases, native app
wrappers, VR/AR modes, user-generated content.

## 6. Existing System / Literature Overview

Commercial lane runners (e.g. the Subway Surfers family) popularised the
three-lane dodge/collect loop, swipe input grammar and chunk-streamed worlds.
Academic and engine literature relevant to this project includes:

- **Chunked world streaming** — the standard "object pool + recycle behind camera" technique used by infinite-runner templates; this project extends it with per-chunk decoration prototypes cloned from a shared cache.
- **Procedural content generation (PCG)** — template + constraint-based generation (as in Togelius et al.'s survey of PCG in games); here, every obstacle row template is validated by a passability predicate and fuzz-tested over thousands of seeds.
- **Bounding-volume collision** — AABB tests with axis-separated broad phase (Ericson, *Real-Time Collision Detection*).
- **Frame-rate independent damping** — exponential smoothing `lerp(a, b, 1-e^{-λΔt})` for camera, lanes and poses.
- **Tone mapping & colour management** — ACES filmic curve and sRGB output, mirroring modern engine practice.
- **Web Audio synthesis** — oscillator/noise-buffer SFX and a lookahead-scheduled music loop (standard Web Audio API scheduling pattern).

Unlike template projects, this implementation keeps all balance values in a
single configuration module, isolates pure logic for unit testing, and ships a
fairness proof-style test suite for its generator.

## 7. Proposed System

A client-only web application. At boot the game builds a renderer, pre-bakes
procedural textures and decoration prototypes with a visible progress bar, and
enters an attract-mode menu over a live 3D scene. A run streams recycled track
chunks and pooled entities toward a fixed-position player (treadmill model),
while distance-space scheduling places obstacle rows, coin patterns and
power-ups. Collisions, scoring, lives, power-up timers and difficulty stages
run as pure logic; rendering consumes their state each frame.

## 8. Technology Stack

TypeScript 5.6 (strict, no `any` leaks), Vite 5 (dev server, bundling,
relative-base static output), Three.js r169 (WebGL renderer, scene graph,
materials, shadow maps, Points/ShaderMaterial particles), Vitest 2 (unit
tests), ESLint 9 + typescript-eslint (static analysis), Web Audio API (audio),
CSS3 custom properties + grid/flex (UI). No backend, no database, no paid
services, no API keys.

## 9. System Architecture

```
┌─────────────── UI (DOM) ───────────────┐   callbacks / CustomEvents   ┌──────── Simulation (WebGL) ────────┐
│ UIManager: screens, HUD, settings,     │ ◄──────────────────────────► │ Game (FSM) → GameLoop (Δt clamp) │
│ toasts, debug overlay                  │                              │   ├ DifficultySystem (pure)      │
└────────────────────────────────────────┘                              │   ├ ScoreSystem (pure)           │
                                                                        │   ├ PowerUpTimers (pure)         │
 StorageManager ⇄ SettingsManager ⇄ AudioManager                        │   ├ SpawnSystem ⇄ PatternPlanner │
                                                                        │   ├ CollisionSystem (pure AABB)  │
 World(renderer/lights/fog) · TrackManager(chunks) · EnvironmentFactory │   ├ ParticleSystem (GLSL Points) │
 Player(rig) · Obstacle/Coin/PowerUp(pooled) · CameraSystem             │   └ CameraSystem                 │
                                                                        └──────────────────────────────────┘
```

Module responsibilities (full file list in README):

- **Game** — finite state machine (boot/loading/menu/playing/paused/gameover), subsystem wiring, input routing, collision orchestration, debug hooks.
- **GameLoop** — `requestAnimationFrame` driver; Δt clamped to 50 ms; FPS meter; visibility auto-pause.
- **World** — renderer setup (ACES, sRGB, PCFSoft shadows), hemisphere + directional moon + two point lights, fog, star field, quality switching.
- **TrackManager / ChunkGenerator** — chunk ring recycling; seeded type sequence with variety rules.
- **EnvironmentFactory** — cached geometry/material/texture factory; per-type decoration prototypes; obstacle/coin/power-up mesh builders; shared-material pulsing.
- **Player** — hierarchical rig (hips→torso→head/arms; hips→thighs→shins) with pose solver (run/jump/slide/hit/jet), lane spring, AABB provider.
- **SpawnSystem** — distance-space row scheduler; entity pools; magnet attraction; despawn/recycle.
- **PatternPlanner** — pure templates + fairness validation + protected-lane rule.
- **ParticleSystem** — single `THREE.Points` cloud, custom vertex/fragment shader, per-particle size/colour/alpha attributes, typed-array pool.
- **CameraSystem** — damped follow, look-ahead, speed FOV, roll lean, shake with decay, landing dip.
- **AudioManager** — lazy AudioContext (first gesture), scheduled music loop, synth SFX, gain graph for master/music/SFX.
- **StorageManager / SettingsManager** — defensive localStorage parse/sanitise; live settings broadcast.
- **UIManager** — all DOM: screens, HUD throttling, power-up chips, toasts, settings form, concepts, debug text.

## 10. Game Loop

Each animation frame: `Δt = min(0.05, now - last)`; if playing → difficulty
integration → distance/score → power-up timers → player pose & physics
(semi-implicit Euler jump) → chunk scroll (`z += v·Δt`) → row scheduling in
*distance space* → entity scroll + magnet → collisions → particles → camera →
throttled HUD → render. Paused frames render the frozen state; hidden tabs
pause automatically and reset the clock to avoid Δt spikes.

## 11. Graphics Pipeline Explanation

Vertex stage: local → world via composed hierarchy matrices (`matrixWorld`),
world → view via the camera's inverse transform (look-at), view → clip via
perspective projection `P(fov, aspect, near, far)`. Fragment stage: PBR
(metalness–roughness) evaluation of hemisphere + directional + point lights,
shadow-map lookup (PCF) for the moon light, fog blend against night colour,
then ACES tone mapping and sRGB encoding. Unlit `MeshBasicMaterial` emissives
and additive particles bypass lighting for neon punch. Custom point-sprite
shader scales `gl_PointSize` by inverse view depth for perspective-correct
particle sizes.

## 12. Transformations

- **Translation**: chunk/coin/obstacle scroll; player lane spring on X.
- **Rotation**: coin spin, power-up tumble, drone rotors, camera roll lean, character joint pivots.
- **Scaling**: unit-box meshes scaled per prop; landing squash; instance matrices for buildings/sleepers.
- **Hierarchy**: shoulder/thigh pivots carry forearms/shins; model-level lean composes over rig poses; decor prototypes clone into chunk groups.

## 13. Projection & Camera

Perspective projection with FOV widened 62°→76° as speed ramps (damped),
aspect from viewport, near 0.1. Follow camera: exponential position damping
behind/above the player, lateral tracking factor 0.55, look-ahead target at
z = −9, roll proportional to lateral velocity, decaying pseudo-random shake
(setting-toggleable), landing dip impulse, and an orbiting attract-mode camera
for the menu.

## 14. Lighting

Night budget: 1 hemisphere (sky/ground bounce), 1 shadow-casting directional
"moon" with a tight ortho frustum around the action, 2 point lights (cyan
player rim, magenta accent) — four lights total, plus emissive materials for
neon. Emissive intensity pulses on warning lamps and holograms animate shared
materials (zero per-object cost).

## 15. Materials & Textures

`MeshStandardMaterial` (PBR) for character, track, props; `MeshBasicMaterial`
for unlit neon signage/bulbs; additive `ShaderMaterial` for particles;
transparent double-sided additive bubble for the shield. All textures are
`CanvasTexture`s drawn procedurally: window grids, neon signs with fictional
names, holo ads with scanlines, train livery, hazard stripes, tunnel tiles,
coin faces, particle sprites — demonstrating UV mapping and repeat wrapping
without shipping a single image file.

## 16. Collision Detection

AABB per entity from deterministic per-kind dimensions (not mesh bounds),
updated on move. Broad phase: Z-window reject. Narrow phase: strict
axis-separated overlap. Pose-dependent player box (standing 1.72 m vs sliding
0.75 m) is what makes jump/slide obstacles honest; jump apex (v²/2g ≈ 1.63 m)
clears 0.95 m barriers with margin. Coins/power-ups use the same pipeline with
generous boxes. Fuzz-tested in Vitest.

## 17. Procedural Generation

Seeded mulberry32 PRNG per run (seed shown in debug overlay). Chunk type
sequence obeys variety rules (no 3-in-a-row, no double tunnels, 3-chunk
"open" grace start). Obstacle rows come from stage-gated templates; a row is
**valid iff** ≥1 lane has no impassable obstacle AND (some passable lane is
empty OR all passable-lane obstacles share one clearable action). Forced
switches set a *protected lane* for the next row and add a grace gap, so the
player is never yanked twice within reaction time. Coin patterns (line/arc/
zigzag/switch/lead-in) are placed only in passable lanes, with heights matched
to the required action (arc over barriers, low line under signs). 6 000+ rows
are fuzz-validated per test run.

## 18. Algorithms & Data Structures

Object pools with free-lists (entities, particles, chunks); round-robin
particle slot allocator; distance-space scheduling queue; reverse-iteration
removal for O(n) despawn; exponential damping; seeded LCG-style PRNG;
throttled DOM updates; reverse-Z broad-phase reject.

## 19. Performance Optimisation

Shared unit geometry + material cache; cloned decor prototypes (geometry
shared, never rebuilt mid-run); `InstancedMesh` for repeated props; single
shadow light with 0.5–2k maps per preset; capped DPR; fog hiding the recycle
plane; HUD at ~12 Hz; typed arrays for particles; Δt clamp; pause-time
simulation freeze; quality presets scaling pixel ratio, shadows, draw
distance, particle cap, decor density and chunk ring size.

## 20. Testing

- **Unit (Vitest, 74 tests)**: score math & multiplier stacking, difficulty ramp/stage bounds & fairness ratio, pattern fuzzing (passability, no double-lane stacking, protected lane, coin safety, seed reproducibility), lane clamping & jump/slide geometry, AABB cases, power-up timers, storage sanitising, config validation, pooling semantics, chunk sequence rules, math utils.
- **E2E (headless Chromium, production build)**: boot → menu → navigation → settings persistence → play → lanes/jump/slide → spawn & collision observation → debug overlay → pause/freeze/resume → touch swipe via CDP → game over → persistence → restart reset → menu → responsive resize → **zero console errors**.

## 21. Results

All required commands pass: `npm install`, `npm run lint`, `npm run test`
(74/74), `npm run build` (≈98 KB game code + 482 KB Three.js chunk, ≈153 KB
gzip total). Headless E2E validates the full play session. On hardware GPUs
the medium preset targets 60 FPS at 1080p-class resolutions; software
renderers remain playable on Low.

## 22. Limitations

Straight track only (curves would complicate the fairness proof and AABB
model); procedural (unrigged) character; shadow frustum covers the player
neighbourhood; music is a minimal procedural loop; software-renderer frame
rates depend on CPU; no post-processing bloom (kept optional by design).

## 23. Future Scope

Spline-warped curved chunks; skinned-mesh hero with animation blending;
optional EffectComposer bloom/DOF on High; seeded daily runs shared by URL;
gamepad + richer accessibility; WebGPU backend; leaderboards via static
hosting + hash seeds.

## 24. Conclusion

Neon Metro Rush meets every stated objective: it is a complete, original,
test-verified 3D endless runner that makes the computer-graphics curriculum
*tangible* — every concept in the syllabus is visible on screen and named in
the in-game Graphics Concepts panel — while shipping with the engineering
discipline (strict typing, lint, tests, pooling, disposal, defensive error
handling) expected of production software.
